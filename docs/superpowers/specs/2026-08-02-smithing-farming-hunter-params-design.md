# Smithing, Farming and Hunter params audit

Date: 2026-08-02

## Problem

`lib/Database.ini` backs the `+params <skill> <query>` command. The combat and
Slayer sections are generated by `reinze-lib-runescape/bin/cmb-xp.py` and are out
of scope. Every other section is hand-maintained and drifts.

Twelve sections have now been audited against the wiki: Cooking, Thieving,
Woodcutting, Fletching, Firemaking, Runecraft, Mining, Fishing, Agility,
Herblore, and — on 2026-08-01 — Prayer and Construction.

This spec covers Smithing (259 entries), Farming (68) and Hunter (76). Two
sections remain unaudited afterwards: Crafting and Magic.

Hunter's history is misleading: commit `bb39a3c` only added goat hunting. The
section has never had a full pass and carries the same drift as the others.

### How lookup works

`reinze-lib-runescape/src/params.rs` selects the section by capitalised skill
name and filters keys with a **case-insensitive substring match**, after
replacing the user's spaces with underscores. Results are capped at 10 and the
key is echoed back with underscores turned into spaces. So a key holding a
literal space is unmatchable, and markup in a key is user-visible.

### Confirmed faults

Smithing — 259 entries, all values plain numbers, no structural faults. One
near-duplicate pair: `4_Cannon_Balls` and `4_Cannonballs`, both `25.6`.

Farming — 68 entries. Four carry a literal `N/A` inside the composite value:

```
Belladonna=92-N/A-512
Bittercap_Mushroom=61.5-N/A-57.7
Evil_Turnip=41-N/A-46
Nightshade=92-N/A-512
```

These render as `92-N/A-512xp`. The wiki has real numbers or genuinely omits the
field; either way `N/A` should not ship.

Hunter — 76 entries, four hyphenated keys (`Barb-tailed_kebbit`,
`Razor-backed_kebbit`, `Sabre-toothed_kebbit`, `Sabre-toothed_kyatt`), all
genuine wiki names that must be preserved.

## Data sources

Each section has a different source. All are enumerated through the transclusion
API (`action=query&list=embeddedin&eititle=<TEMPLATE>&einamespace=0&eilimit=500`,
following `continue`), with page wikitext from `?action=raw`.

**Farming** — `{{Farming info}}`, 255 mainspace transclusions. Fields `name`,
`level`, `plantxp`, `checkxp`, `harvestxp`. Lives on the *plant* page, not the
seed page: `Apple tree` has it, `Acorn` does not.

**Hunter** — `{{Hunter info}}`, 89 transclusions. Fields `name`, `level`, `xp`,
`wildxp`.

**Smithing** — no dedicated template. Values come from `{{Recipe}}`, which has
3,724 transclusions across every skill, filtered to those where any `skillN` is
`Smithing`, reading `outputN` and the matching `skillNexp`:

```
{{Recipe
|skill1 = Smithing
|skill1lvl = 99
|skill1exp = 375
|mat1 = Runite bar
|output1 = Rune platebody
}}
```

Smithing is sometimes a secondary skill, so `skill2` and `skill3` are checked
too. The sweep is roughly 3,700 fetches — about ten minutes once, then cached.

## Value encoding

Farming and Hunter pack several numbers into one value. Both conventions map
directly onto their template fields and are kept:

| Section | Encoding | Meaning | Example |
| --- | --- | --- | --- |
| Farming | `-` joined | `plantxp`, `checkxp`, `harvestxp` — whichever exist | `Apple_Tree=22-1199.5-8.5` |
| Farming | `-` joined | plant and check only (trees) | `Acorn_Oak_Tree=14-467.3` |
| Farming | `-` joined | plant and harvest only (allotments) | `Asgarnian_Hops=10.5-12` |
| Hunter | `/` joined | `xp` / `wildxp` | `Baby_impling=18/20` |
| Hunter | `-` joined | level-scaled XP range | `Herbiboar=1950-2461` |
| Both | bare | single value | `Barb-tailed_kebbit=168` |

**Hunter uses `-` and `/` with different meanings in the same section.** `/`
separates the normal and Wilderness values for the eleven implings. `-` is a
range across Hunter levels, used by `Herbiboar=1950-2461` and
`Wyrmscraig_goat=100-179`. `{{Hunter info}}` carries `xp` and `wildxp` but not
the range, so those two entries are hand-kept and verified against their pages
rather than generated. This is a wrinkle worth preserving rather than
normalising: both readings are established and users see them.

## Approach

The audit tool built on 2026-08-01 is reused. `fetch.py` (transclusion
enumeration, disk cache, rate limiting) and `reconcile.py` (four-bucket diff,
ambiguity detection, case-collision guard) are skill-agnostic and carry over
with their existing tests. Only parsing is new.

### Interface change: values become strings

`reconcile` currently takes `dict[str, float]` and calls `format_number` to
render. Composite values make that untenable, so `format_number` moves into the
parsers: each parser emits the finished INI value string and `reconcile`
compares strings.

This is a simplification, not a workaround. It removes the float/string
ambiguity that produced the `2230.0` versus `2230` handling, and makes the
composite encodings first-class rather than special cases. The four buckets,
the ambiguity machinery and the collision guard are otherwise unchanged.

### Three parsers

All three return `list[tuple[str, str]]` of `(key, value_string)`. A list rather
than a single optional result because a page can carry more than one template
block — several `{{Recipe}}` blocks for different methods, or a versioned crop —
and a uniform shape lets one collision path serve all three:

- `smithing_entries` — every `{{Recipe}}` block whose `skillN` is Smithing,
  keyed by the matching `outputN`, valued by `skillNexp`.
- `farming_entries` — from `{{Farming info}}`, joining the present `plantxp`,
  `checkxp` and `harvestxp` fields with `-`.
- `hunter_entries` — from `{{Hunter info}}`, joining `xp` and `wildxp` with `/`
  when both exist, otherwise the bare `xp`.

An empty list means the page carries no relevant template, which is a normal
outcome. A field that is present but unparseable is recorded and reported,
never silently dropped.

### Reports and hand edits

The tool produces one reconcile report per section — unchanged, changed,
wiki-only, ini-only, ambiguous, collisions — plus a wiki key-set dump per
section for the final assertions. A human then works each report by hand and
commits one section at a time.

## Contamination risks

Two failure modes from the previous audit apply directly. Both produce
plausible-looking corrections that no test catches.

**Alternate smithing methods.** Giants' Foundry and Blast Furnace award
different XP for the same item, and a single page can carry several `{{Recipe}}`
blocks. This is the same shape as the Mahogany Homes collision that would have
overwritten roughly 24 correct Construction values with minigame rates. Keys are
therefore taken from the page title, and same-key-different-value collisions are
reported for a human rather than resolved by last-write-wins.

**Alpha and beta content.** The wiki documents Sailing alpha/beta items that
never shipped. Every addition is screened for `{{Sailing Beta Content}}`,
`{{Beta}}` and an `|id =` beginning `beta`. This is what caught `Monodon bones`
(id `beta30922`) before it shipped in Prayer. Screening is on the marker, never
on whether an item looks familiar — recency reads identically to unfamiliarity,
and that framing would have wrongly rejected two legitimate Sailing bones.

## Scope decisions

**Add everything the templates cover.** Farming grows from 68 toward ~255,
Hunter from 76 toward ~89, and Smithing is rebuilt from every qualifying
`{{Recipe}}`. This matches the Construction rebuild and avoids an arbitrary
cutoff.

**Keys are the wiki's exact item name** with spaces replaced by underscores.
Hyphens survive only where the wiki name genuinely has one.

**Farming keys move to wiki plant names.** `Acorn_Oak_Tree` becomes `Oak_tree`,
so a query for `acorn` no longer finds it. This is consistent with the rule
applied to every audited section, and was accepted deliberately.

**The `N/A` values are resolved** against each plant's page — either the real
number, or the field dropped from the composite.

**Deduplicate `4_Cannon_Balls` / `4_Cannonballs`** to the wiki name.

## Out of scope

- `Attack`, `Strength`, `Defence`, `Ranged`, `Hitpoints`, `Slayer` — script
  generated, consolidation with `npc/data.rs` pending.
- `Crafting` and `Magic` — the remaining unaudited sections, for a later pass.
  Magic in particular needs different tooling, since spells use
  `{{Infobox Spell}}` rather than item-page templates.
- The 10-result display cap in `params.rs:50`. Already user-visible: after the
  Prayer audit, `+params prayer bones` matches 43 entries and `Dragon_bones` no
  longer appears in its output. Growing Farming and Smithing will make
  truncation more common. This is a code change and is flagged, not fixed.
- Any other skill section.

## The tool is not committed

It lives in the job's temp directory, as before. Every commit in this series
touches `lib/Database.ini` alone.

## Verification

- Mechanical scan per section, with a **per-section value grammar** rather than
  one bare-number rule:
  - Smithing `\d+(\.\d+)?`
  - Farming `\d+(\.\d+)?(-\d+(\.\d+)?){0,2}`
  - Hunter `\d+(\.\d+)?([/-]\d+(\.\d+)?)?`
  Plus: no empty values, no literal spaces in keys, no wiki markup, no
  case-duplicate keys, alphabetically sorted, and every key either in the
  section's wiki key set or in a documented hand-kept allowlist.
- No `N/A` remains in any Farming value.
- The INI still parses under the crate the bot uses (`rust-ini 0.21`). Since
  `rust-reinze` has no cargo dependency on `reinze-lib-runescape` — plugins load
  at runtime as `.so` files — this runs as a throwaway `examples/` binary inside
  the plugin repo and is deleted immediately after.
- `cargo test` in `reinze-lib-runescape` passes. This proves nothing about the
  data: both `params.rs` tests return before `Ini::load_from_file`. The check
  above is the one that matters.
- Spot-check a sample of changed values against their own wiki pages.
- The other 20 sections are byte-identical.
