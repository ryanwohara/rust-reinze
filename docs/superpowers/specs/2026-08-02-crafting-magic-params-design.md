# Crafting and Magic params audit, and result ranking

Date: 2026-08-02

## Problem

`lib/Database.ini` backs the `+params <skill> <query>` command. Combat and
Slayer are generated by `reinze-lib-runescape/bin/cmb-xp.py` and are out of
scope. Every other section is hand-maintained and drifts.

Five sections have been audited: Prayer and Construction on 2026-08-01,
Smithing, Farming and Hunter on 2026-08-02. **Crafting (118 entries) and
Magic (160) are the last two.** After this, the hand-maintained half of the
file has been fully re-derived from the wiki.

This spec also fixes a lookup defect the audits made measurable.

### How lookup works

`reinze-lib-runescape/src/params.rs` selects the section by capitalised skill
name, then filters keys with a **case-insensitive substring match** after
replacing the user's spaces with underscores. It takes the **first 10**
results in file order and echoes each key back with underscores turned into
spaces.

File order is alphabetical, so the cap silently returns an arbitrary
alphabetical slice rather than the most relevant matches.

### The cap defect, measured

Growing the sections made this visible:

```
+params smithing cannonball   18 matches; Steel_cannonball at rank 16, invisible
+params smithing bar          15 matches; mithril, runite, silver, steel all hidden
+params hitpoints goblin      15 matches; answers with Angry_goblin_(lvl_47)
+params attack dragon         14 matches; answers with three baby dragons
```

The unaudited sections are the worst affected, not the audited ones — each
combat section holds 637 entries. This is a pre-existing bug that the audits
exposed rather than caused.

### Confirmed faults in the two sections

**Neither section has a structural fault.** No empty values, no literal
spaces in keys, no case-duplicate keys, no near-duplicate keys, and every
value is already a plain number. Crafting has two hyphenated keys
(`Yak-hide_legs`, `Yak-hide_body`), both genuine wiki names.

So this is a value-correctness and coverage audit, not a repair job — the
opposite of what Construction needed.

## Part 1 — Result ranking

### The change

`params.rs` currently does `filter(contains) → take(10)`. It will instead
collect every match, rank it, then take 10.

| Tier | Condition |
| --- | --- |
| 0 | key equals the query, case-insensitively |
| 1 | key starts with the query |
| 2 | key contains the query |

Ties break by **fewest extra underscore-separated tokens**, then
**alphabetically**.

"Extra tokens" means the key's token count minus the query's, where both are
counted after the query's spaces become underscores: `bird house` is two
tokens, `Bird_house` is two, so that pair has zero extra. The value is
clamped at zero so a key shorter than the query cannot sort ahead of an exact
match.

The token count is what surfaces a buried canonical answer: for the query
`cannonball`, `Steel_cannonball` has one extra token and
`Adamant_chainshot_cannonball` has two, so the plain cannonballs rise above
the chainshot and incendiary variants.

The alphabetical final tiebreak is what preserves coherence when matches are
peers. An earlier draft of this design used key *length* instead, which fixed
`cannonball` but scrambled `+params magic teleport` — 31 alphabetically
ordered teleports became `Teleport_Catherby, House_Teleport, Lassar_Teleport`.
Token count leaves that list alone.

### Measured effect

| Query | Today | After |
| --- | --- | --- |
| `hitpoints goblin` | `Angry_goblin_(lvl_47)`, `Angry_goblin_(lvl_45)`, … | `Goblin_Champion`, `Goblin_(lvl_11)`, … |
| `attack dragon` | `Baby_black_dragon`, `Baby_blue_dragon`, … | `Black_Dragon`, `Blue_Dragon`, `Bronze_dragon`, … |
| `smithing cannonball` | `Steel_cannonball` at rank 16 | at rank 6 |
| `smithing bar` | `'perfect'_gold_bar` first | plain bars first |
| `magic teleport` | alphabetical | unchanged, except `Teleport_Catherby` promoted as a genuine prefix match |
| `slayer kalphite` | — | identical |
| `hunter bird house` | — | identical |

No value changes and no match disappears. Only the order within the matched
set changes, and only where a shorter or more exact key was being outranked.

### Why it applies to every section

`lookup` is one generic function serving all 23 sections. Scoping the change
would mean hardcoding a list of audited skill names into the lookup and
extending it on every future audit — arbitrary, and permanent maintenance for
a temporary distinction. The unaudited sections also benefit most, being the
largest and most truncated.

### Testability

`params.rs` has two tests today and both deliberately return before
`Ini::load_from_file`, so the suite never touches the data file. To keep that
property, the ranking is extracted into a **pure function** taking the keys
and the query and returning them ranked. `lookup` calls it. The function is
unit-tested directly with no INI, no fixture file and no network.

## Part 2 — The data audit

### Sources

**Crafting** — `{{Recipe}}`, the same generic template Smithing used,
filtered to blocks whose `skillN` is `Crafting`, reading `outputN` and the
matching `skillNexp`. 508 distinct keys against the INI's 118.

**Magic** — `{{Infobox Spell}}`, 226 mainspace transclusions with fields
`name`, `level`, `spellbook`, `exp`. This is the cleanest corpus of the whole
audit: 224 pages carry a plain numeric `exp`, none uses versioned fields, and
none is missing one. Spellbooks break down as Normal 82, Ancient 25, Lunar
44, Arceuus 70, and three marked "all".

### Tool changes

The audit tool is reused. `smithing_entries` is generalised to
`recipe_entries(wikitext, skill)` and both callers use it — Smithing is
already committed and will not be re-derived, so this is pure deduplication.
A new `magic_entries` reads `{{Infobox Spell}}`.

### Edge cases already found

- **9 Crafting ambiguities**, all shapes already ruled on in the Smithing
  audit. `Purging_staff` 730 vs 73 is first-time versus subsequent, exactly
  like `Emberlight`. `Molten_glass` 20/130/180 and `Bow_string` 15/75 are
  alternate methods. `Blade_of_saeldor_(c)`, `Bow_of_faerdhinen_(c)`,
  `Crystal_felling_axe` and `Salve_amulet` are zero versus real.
  `Armadylean_plate` 210/840/630 and `Crushed_gem` 3.7/5/6.3 are tiers and
  need individual resolution.
- **`Fishing Crane#Repaired`** — the `output1` carries a `#` anchor. Strip it
  or exclude the entry; a `#` must not reach a key.
- **`Guardian essence: skill1exp = '1-5'`** — a range in a section whose
  grammar is bare numbers. Resolved by hand.
- **`Alchemic Divergence` and `Alchemic Convergence`: `exp = '10 * items'`** —
  formulae with no fixed value, like Hunter's Moss Lizard. Resolved by hand,
  with no invented number.

### Standing rules carried forward

Each was established by an earlier section and now applies to every addition:

- **Alpha/beta screen** — reject `{{Sailing Beta Content}}` (with or without a
  parameter), `{{Beta}}`, or an `|id =` beginning `beta`.
- **Removed-from-game screen** — reject `{{Gone}}` or an `|id =` beginning
  `hist`.
- **Sanity-check every screen against a known positive before trusting a zero
  result.** The literal-string form of the beta marker misses
  `{{Sailing Beta Content|alpha}}`; three separate agents hit this and each
  caught it only by testing against `Monodon bones`.
- **Zero-XP rows excluded**, and for a composite value only when every
  component is zero.
- **Keys are the wiki's exact item name** with spaces replaced by `_`.
  Hyphens survive only where the wiki name genuinely has one.
- **Every INI-only entry is decided individually**, and dropped only as a
  duplicate, superseded, or demonstrably not Old School.

### Scope

Add everything the templates cover: Crafting 118 toward ~508, Magic 160
toward ~224. This matches every prior section and avoids a cutoff that would
have to be defended entry by entry. The ranking fix in Part 1 is what keeps
the larger Crafting section queryable.

## Out of scope

- `Attack`, `Strength`, `Defence`, `Ranged`, `Hitpoints`, `Slayer` — script
  generated, consolidation with `npc/data.rs` pending. Their *content* is
  untouched; only the order results are displayed in changes, via Part 1.
- The other audited sections' data. Prayer, Construction, Smithing, Farming
  and Hunter stay byte-identical.
- Raising the 10-result cap. Ranking makes the visible 10 relevant, which is
  the cheaper fix for an IRC bot where 40 lines of output would be worse.

## Verification

- Mechanical scan per section: no empty values, no literal spaces or wiki
  markup in keys, bare numeric values, no case-duplicate keys, alphabetically
  sorted, and every key either in the section's wiki key set or in a
  documented hand-kept allowlist.
- The INI still parses under `rust-ini 0.21`, run as a throwaway `examples/`
  binary inside `reinze-lib-runescape` and deleted immediately after, since
  `rust-reinze` has no cargo dependency on that crate.
- `cargo test` in `reinze-lib-runescape` passes, now including the new
  ranking tests. Note that unlike previous audits this DOES exercise part of
  the change — the ranking function is genuinely unit-tested — but it still
  proves nothing about the INI's data, so the check above remains the one
  that matters for Part 2.
- The ranking's measured effects are re-confirmed against the finished file
  for the queries tabulated above.
- The 20 sections not named in this spec are byte-identical.
- CRLF line endings preserved. The file uses them throughout.

## Deliverable

Three commits across two repositories.

In `reinze-lib-runescape`, matching its conventional-commit style:

```
feat(params): rank exact and prefix matches above substrings
```

In `rust-reinze`:

```
chore(data): Update Crafting params from wiki
chore(data): Update Magic params from wiki
```

Each data commit body states what changed and why, including what was
deliberately left alone.
